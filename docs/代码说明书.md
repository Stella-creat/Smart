### 0.3 分层与调用方向

```
浏览器（web/index.html）
   │  REST + JWT（/api/*，:8004）
   ▼
FastAPI 路由层（api/routers/*.py）        ← 只做参数校验、鉴权、异常转 HTTP 码
   │
   ▼
业务服务层（knowledge / question / plan / practice / user）
   │  只依赖 AIProvider 抽象，不 import DeepTutor
   ▼
适配层（adapter/）
   ├── container.get_ai_provider() → DeepTutorProvider
   ├── REST：知识库元数据（/api/knowledge-bases/*）
   └── WebSocket：AI 能力（ws://:8001/ws，start_turn）
   │
   ▼
DeepTutor 引擎 → DeepSeek LLM / SiliconFlow Embedding
```

**数据流向原则**：业务数据（用户、知识点、题目、计划、答题记录）全部写在本项目的 SQLite/MySQL；DeepTutor 只提供「内容与 AI 能力」，本系统不写引擎库，引擎也不读业务库。二者通过适配层的映射表（chunk_ref ↔ kp_id）单向关联。

| `db_url` | `sqlite:///./smart_dev.db` | 数据库连接串；注释中给出 MySQL 写法 `mysql+aiomysql://...` |

| `jwt_expire_minutes` | `1440` | Token 有效期 24 小时 |

模块末尾导出单例 `settings`，其他模块统一 `from smart.config import settings`。

### 1.2 `src/smart/db.py` — 连接与会话

| 成员 | 说明 |
| --- | --- |
| `engine` | `create_engine(settings.db_url, echo=settings.debug, future=True)`；SQLite 追加 `check_same_thread=False`，否则 FastAPI 多线程下会报错 |
| `SessionLocal` | `sessionmaker`，`autoflush=False`、`expire_on_commit=False`（提交后对象仍可读，避免在路由里二次查询） |

| `init_db()` | 导入 `models` 触发建表注册，然后 `Base.metadata.create_all()`。**仅用于开发期**，无迁移能力（后续应上 Alembic） |

### 1.3 `src/smart/db_utils.py` — 序列化工具

`to_dict(obj)` 遍历 `obj.__table__.columns`，只保留真实列，过滤 `_sa_instance_state` 等内部属性；`datetime` 统一转 ISO 字符串，`JSON` 列原样返回。`to_dict_list()` 是批量版本。

路由层不定义 response_model，直接返回 `to_dict(...)`，这样字段增删不需要同步改 schema。

### 1.4 `src/smart/api/main.py` — 应用入口

| 代码位置 | 作用 |

## 2. 数据模型 `models.py`

### 2.1 业务枚举

| 枚举 | 取值 | 用途 |
| --- | --- | --- |
| `QuestionType` | 1 单选 / 2 多选 / 3 判断 / 4 填空 / 5 简答 | `t_question.type` |
| `Difficulty` | 1 简单 / 2 中等 / 3 困难 | `t_question.difficulty` |
| `QuestionSource` | `IMPORT` / `AI` / `MANUAL` | 题目来源，前端据此标识 |
| `TaskStatus` | 0 待完成 / 1 已完成 / 2 已跳过 | 计划任务状态 |
| `TaskType` | `REVIEW` / `PRACTICE` | 复习轨 / 练习轨 |
| `KnowledgeType` | `memory` / `concept` / `procedure` / `design` | 决定遗忘曲线间隔序列 |

`_utcnow()` 统一生成「UTC 时间但去掉 tzinfo」的 naive datetime，避免 SQLite 与 MySQL 时区行为差异。

### 2.2 十张表

| 表名 | 用途 | 关键字段 | 主要读写方 |
| --- | --- | --- | --- |
| `t_user` | 用户账号 | `username` 唯一、`password_hash`、`role` | `user/service.py` |
| `t_knowledge_point` | 三级知识点树 + 掌握度状态 | `user_id`（0=系统内置）、`subject/chapter/name`、`parent_id`、`mastery`、`mastery_count`、`next_review_time`、`interval_index`、`consecutive_correct/wrong` | `knowledge`、`plan`、`practice` |
| `t_question` | 题库 | `knowledge_point_id`、`type`、`difficulty`、`content`、`options`(JSON)、`answer`、`source` | `question`、`practice` |
| `t_learning_plan` | 学习计划 | `user_id`、`subject`、`exam_date`、`daily_minutes`、`status`(1 进行中) | `plan` |
| `t_plan_task` | 每日任务 | `plan_id`、`knowledge_point_id`、`task_type`、`task_date`、`status`、`duration_minutes`、`actual_duration`、`question_ids`(JSON) | `plan`、`practice` |
| `t_mapping_alias` | L2 别名表 | `alias`（统一小写入库）、`kp_id`、`source`(MANUAL/REVIEW_AUTO) | `pipeline`、`mapping` |
| `t_mapping_staging` | 映射暂存隔离区 | `source_type`、`source_ref`、`source_text`、`kp_id`、`match_level`、`confidence`、`status`(0 待审/1 通过/2 拒绝) | `pipeline`、`mapping` |
| `t_mapping_chunk_point` | 正式映射表 | `chunk_ref`（唯一语义）、`kp_id`、`confidence` | `pipeline`、`mapping`；业务检索入口 |
| `t_attempt_record` | 每次答题/打卡 | `knowledge_point_id`、`task_id`、`is_correct`、`duration_seconds` | `question.submit_and_judge`、`plan` |
| `t_practice_record` | 练习逐题明细 | `task_id`、`question_id`、`user_answer`、`score`、`is_correct`、`feedback` | `practice` |

设计要点：

- **`user_id = 0` 表示系统内置数据**，所有查询用 `(user_id == 当前用户) | (user_id == 0)` 兼容内置与私有数据。
- **`t_attempt_record` 与 `t_practice_record` 分工**：前者是掌握度算法的输入（每题一条对错），后者是练习页面的作答明细（含用户答案、得分、反馈），由 `practice.submit` 同时写入两者。
- `KnowledgePoint` 自引用 `parent`/`children`，`cascade="all, delete-orphan"`，删父节点会级联删子节点。

## 5. 映射适配层（核心）

### 5.1 设计意图

业务层禁止 `import deeptutor`，只面向 `AIProvider` 编程。这样做的收益：

1. **防腐**：DeepTutor 的协议变更（字段、事件名）只影响 `deep_tutor_provider.py` 一个文件；
2. **可替换**：换成 DeepSeek 直连或其他平台，只需新增一个实现类并在容器里换绑，业务表和业务代码零改动；
3. **数据主权**：引擎只被读取，业务库不被外部写入。

### 5.2 `adapter/provider/ai_provider.py`

四个数据类 + 一个 Protocol：

| 类型 | 字段 | 说明 |
| --- | --- | --- |
| `KBInfo` | `name`、`description`、`status` | 知识库元信息 |
| `Chunk` | `ref`、`text`、`source_doc`、`score` | RAG 检索片段；`ref` 是映射表的外键 |
| `GeneratedQuestion` | `content`、`type`、`difficulty`、`options`、`answer`、`explanation` | AI 出题结果 |
| `JudgeResult` | `score`(0–100)、`is_correct`、`feedback` | 判分结果 |

`AIProvider` 是 `runtime_checkable` 的 Protocol，共 10 个方法：

| 分类 | 方法 |
| --- | --- |
| 知识库 | `list_knowledge_bases`、`list_documents`、`retrieve_chunks`、`create_knowledge_base`、`upload_documents`、`web_search` |
| 出题 | `generate_questions(context_chunks, types, difficulty, count)` |
| 判分 | `judge_answer(question_content, reference_answer, user_answer)` |
| 语义 | `semantic_similarity(text_a, text_b) -> float` |
| 已弃用 | `embed(texts)`（保留签名兼容，见 5.5） |

### 5.3 `adapter/container.py`

模块级变量 `_provider_instance` 做惰性单例；`get_ai_provider()` 首次调用时构造 `DeepTutorProvider()`；`set_ai_provider(p)` 用于替换实现。

所有路由在每次请求时调 `get_ai_provider()`，因此换绑后无需重启进程内的服务对象（仍建议重启以清理连接）。

### 5.4 `adapter/provider/deep_tutor_provider.py`

#### 5.4.1 双通道

| 通道 | 用途 | 实现 |
| --- | --- | --- |
| REST（`httpx.Client`，base_url=引擎地址） | 知识库元数据：列表、文档、建库、上传、reindex、配置查询 | 同步请求，超时 15s；上传 300s；reindex 60s |
| WebSocket（`ws://…/ws`） | 所有 LLM 能力：检索、出题、判分、语义相似度、联网搜索 | 每个请求独立连接，协议 v2.0 `start_turn` |

构造时 `_find_deeptutor_data_dir()` 尝试定位引擎的 `data/knowledge_bases` 目录，作为 REST 不可用时的本地文件兜底（仅在源码环境有效）。

#### 5.4.2 WebSocket 协议实现

`_ws_call` 组装 payload：

```json
{
  "type": "start_turn",
  "protocol_version": "2.0",
  "content": "<提示词>",
  "capability": "chat",
  "session_id": "zsk-chat-xxxxxxxx",
  "config": {},
  "knowledge_bases": ["<库名>"],   // 可选；RAG 检索时必带
  "tools": ["rag"]                 // 可选；显式 [] 表示禁用用户可选工具
}
```

> `session_id` 用 `zsk-<capability>-<8位随机>`，保证每次调用是独立会话，不会串上下文。

响应事件循环（`while True`）：

| 事件类型 | 处理 |
| --- | --- |
| `content` | 流式 token，累加到 `accumulated` |
| `result` | 取 `metadata.response`；缺失则回退累计文本，再回退 `content`；**立即返回** |
| `error` | 抛 `RuntimeError`，消息带引擎原文 |
| `done` | 有累计文本则返回，否则跳出循环 |
| 其他（`session`/`progress`/`stage_*`） | 忽略 |

每次 `recv` 有 `timeout` 上限，超时跳出并返回已累计内容（避免半截响应完全丢失）。

`_sync_ws_call(**kwargs)`：为每个调用新建事件循环 `run_until_complete`，用完关闭。这样同步路由可直接调用，不需要把整条业务链改成 async；异常一律吞掉并返回 `""`，由上层走降级逻辑（注意：这也意味着排查问题要看引擎侧日志或临时打点）。

#### 5.4.3 数据方法

| 方法 | 实现与降级 |
| --- | --- |
| `list_knowledge_bases` | `GET /api/knowledge-bases/configs`，解析 `knowledge_bases` 字典；HTTP 异常时读本地 `data/knowledge_bases` 目录名，再不行返回 `[]` |
| `list_documents` | `GET /api/knowledge-bases/{kb}/files`；异常时读本地 `<kb>/raw` 目录 |
| `create_knowledge_base` | `POST /api/knowledge-bases`，表单 `name`；返回 `{"name": ...}` 合并引擎响应 |
| `upload_documents` | `POST /api/knowledge-bases/{kb}/upload`（multipart，300s）→ 随后 `GET .../config` 检查 `index_versions`；为空说明新库索引未初始化，补 `POST .../reindex`。目的是规避新库直接上传时报 “Knowledge base not initialized” |
| `retrieve_chunks` | WS `chat` + `knowledge_bases=[kb]` + `tools=["rag"]`，提示词要求只返回 JSON 数组（`text`/`source_doc`/`score`）；`Chunk.ref` 拼接为 `<kb>#<序号>` |
| `generate_questions` | WS 出题提示词（见下），解析后映射为 `GeneratedQuestion` |
| `judge_answer` | WS 判分提示词，要求 `{"score","is_correct","feedback"}` |
| `semantic_similarity` | WS，`_SIM_PROMPT` 要求 `{"score": 0.0~1.0}`，结果裁剪到 `[0,1]` |
| `web_search` | WS `chat` + `tools=["web_search"]`，返回带来源的答案文本 |
| `embed` | **已弃用**：返回 SHA-256 派生的 128 维伪向量，只为签名兼容；调用方应改用 `semantic_similarity` |

**出题提示词要点**：拼最多 3 段上下文（每段截断 500 字），字段约定 `content/type/difficulty/options/answer/explanation`，并明确「直接输出 JSON 数组、不写文件、不调用工具、不加说明文字」。调用参数为 `tools=[]`。

#### 5.4.4 解析容错三件套

LLM 输出形态不稳定，因此分三层：

| 方法 | 用途 |
| --- | --- |
| `_extract_json_array(text)` | 正则 `\[.*\]`（DOTALL）截取数组，容忍前后散文与 ``` 代码块；解析失败返回 None |
| `_extract_json_object(text)` | 正则 `\{.*\}` 截取对象，用于判分/相似度 |
| `_fetch_output_json(text)` | 兜底：LLM 把结果写进文件时，正文会出现 `outputs/...*.json` 链接；提取该路径，请求引擎 `/files/outputs/...` 取回并解析为数组 |

三层都失败才返回空结果。`generate_questions` 返回空列表 → 路由返回 `saved: 0`。这正是此前「AI 出题入库 0 道」的根因，现已修复。

### 5.5 `adapter/matcher/pipeline.py`

目的：把引擎侧扁平 chunk 映射到本系统的三级知识点树。

| 级别 | 函数 | 判定规则 | 命中置信度 |
| --- | --- | --- | --- |
| L1 | `match_exact` | `chunk.source_doc`（或 `ref`）规范化后与 `subject/chapter/name` 拼接路径**双向包含** | 1.0 |
| L2 | `match_alias` | 遍历 `t_mapping_alias`，`alias` 出现在 chunk 文本+来源路径中（子串包含） | 0.95 |
| L3 | `match_semantic` | 逐 KP 调用 `provider.semantic_similarity(chunk.text[:300], "subject chapter name")`，取最高分 | 由 LLM 给出 |
| L4 | 审核队列 | 最高分落在 `[0.60, 0.85)` | 原样记录 |

主流程 `run_matching_pipeline`：

- L1/L2/L3 自动通过 → 写 `t_mapping_staging(status=1)` + upsert `t_mapping_chunk_point`（`chunk_ref` 已存在则更新 `kp_id/confidence`）；
- L3 落在审核区间 → 只写 `t_mapping_staging(status=0)`，不写正式表；
- 低于 0.60 或无候选 → `dropped` 计数，不落表；
- 返回计数字典 `{L1_exact, L2_alias, L3_semantic_auto, L4_review, dropped}`，供前端/日志观察。

`upsert_alias(alias, kp_id, source)`：别名统一 `lower()` 入库；已存在则更新 `kp_id`。

> 复杂度提示：L3 是 `chunk × KP` 次 LLM 调用（约 0.5s/次）。同步 50 条 chunk、10 个知识点 ≈ 250 次调用，耗时数分钟。当前实现适合手动触发，不适合高频自动跑。

## 7. 学习计划模块

### 7.1 `plan/service.py` — 算法常量

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `_RECENCY_WEIGHTS` | `(0.5, 0.7, 0.85, 0.95, 1.0)` | 越近的答题权重越高 |
| `_CONFIDENCE_CAP` | `{1: 0.5, 2: 0.8}` | 答题次数少时掌握度上限：只答 1 题最多 50%，答 2 题最多 80% |
| `_INTERVAL_DAYS` | memory `[0,1,3,7,14,30,60]`；concept `[3,7,14,30]`；procedure `[3,7,14]`；design `[14,28]` | 不同知识类型的复习间隔序列（天） |

`compute_mastery(correctness)`：取最近 5 条对错，按权重加权求平均，再套用 `_CONFIDENCE_CAP`。例：最近 3 条为 `[对, 错, 对]` → `(0.85*1 + 0.95*0 + 1.0*1)/(0.85+0.95+1.0) ≈ 0.66`。

`_as_date(v)` 统一把 `datetime`/`date` 转 `date`，因为 SQLite 的 `DateTime` 列可能返回任一类型。

### 7.2 计划生成

| 方法 | 行为 |
| --- | --- |
| `create_plan` | 建计划（`status` 默认 1 进行中）→ `_generate_tasks(horizon_days=14)` 预排 14 天 |
| `_generate_tasks` | 逐日调用 `generate_day_tasks(only_missing=False)` |
| `generate_day_tasks(db, plan, task_date, only_missing=True)` | 单日排期（见下） |

**单日排期逻辑**

1. 取该计划科目下的全部知识点（本人 + 内置），按 `(mastery, next_review_time)` 升序，弱势与到期者优先；
2. `remaining_minutes = plan.daily_minutes` 作为时间预算；
3. **复习轨**：`next_review_time` 为空或 ≤ 目标日期的知识点各排一条 `REVIEW`，时长 15 分钟（`mastery >= 55` 则 10 分钟）；排完把该 KP 的 `next_review_time` 顺延 +7 天（避免同轮重复排）；
4. **练习轨**：预算仍 > 15 分钟时，取 `mastery < 60` 的前 3 个知识点排 `PRACTICE`，每条 20 分钟，`question_ids=[]` 占位（实际配题由练习模块完成）；
5. `only_missing=True` 时先查当日已有 `(kp_id, task_type)` 组合，命中的跳过——保证每日回流幂等；
6. 统一 `commit` 并返回新建任务列表。

### 7.3 回流

| 方法 | 行为 |
| --- | --- |
| `rollover_expired_tasks(db, today, max_carry_days=7)` | 所有 `task_date < today` 且 `status=TODO` 的任务：7 天内 → `task_date` 改为今天（顺延）；超过 7 天 → `status=SKIPPED`。返回 `{carried, skipped}` |
| `run_daily_rollover(db, today?)` | ① 先顺延过期任务（**永远对标真实今天**）；② 遍历所有 `status=1` 的计划，为目标日期补齐当日任务；返回 `{date, plans, created_tasks, carried, skipped}` |

`today` 参数只决定「补排哪一天」，不影响过期判定——因此可以用它补跑历史日期而不误伤现有任务。

### 7.4 任务状态与掌握度回流

| 方法 | 行为 |
| --- | --- |
| `today_tasks(db, user_id, plan_id?)` | 查 `task_date = 今天` 的任务 |
| `mark_task_done(db, task_id, is_correct?, actual_duration?)` | 置 `DONE`；仅当 `task_type=PRACTICE` 且 `is_correct` 非空时更新掌握度 |
| `mark_task_skipped` | 置 `SKIPPED` |
| `_update_mastery_and_schedule` | 取该 KP 最近 10 条答题记录 → 拼入本次结果 → `compute_mastery` 写入 `mastery`（×100）→ `mastery_count += 1` → 新增一条 `t_attempt_record` → 推进遗忘曲线 |
| `_advance_schedule` | 答对：连续正确 +1；连续 2 次正确则间隔前进 2 格，否则前进 1 格；答错：连续错误 +1 且间隔回退 1 格。随后 `last_review_time = now`，`next_review_time = now + intervals[index]` 天 |
| `apply_practice_result(db, task, correctness, actual_minutes?)` | 练习结算专用：按**本次全部答题**重算掌握度（`compute_mastery(correctness)`），`mastery_count += 答题数`，正确率 ≥ 60% 视为「本轮答对」推进间隔；置任务 `DONE` |

`apply_practice_result` 与 `mark_task_done` 的区别：后者是「复习打卡/单题对错」，前者是「整份练习一次性结算」，避免逐题重复写 `AttemptRecord`。

### 8.1 `practice/service.py`

## 9. 每日定时回流 `jobs/daily.py`

| 成员 | 说明 |
| --- | --- |
| `_ensure_handler()` | uvicorn 未给本项目 logger 配 handler，这里补一个 StreamHandler，否则 `logger.info` 会被丢弃 |
| `_last_run` | 模块级 `date`，记录「最近一次执行日期」，实现「每天最多一次」 |
| `run_once(target_date?)` | 新开 `SessionLocal` 调 `PlanService.run_daily_rollover`；供定时协程与手动补跑复用 |
| `daily_loop()` | 常驻协程：每 `max(30, interval)` 秒巡检；当 `now.hour >= daily_rollover_hour` 且 `_last_run != today` 时执行一次并记录日志；异常只 `logger.exception`，不中断循环 |

时序：

```
FastAPI startup → asyncio.create_task(daily_loop())
daily_loop 每 5 分钟醒来
  ├─ 未到设定小时 → 继续睡
  ├─ 已到且今天没跑过 → run_once(今天) → 日志「每日回流完成: {...}」
  └─ 异常 → 记录堆栈，继续睡（协程不退出）
```

**限制**：`_last_run` 是进程内状态。多 worker / 多实例部署时每个进程都会跑一遍，需替换为 Redis 分布式锁或独立调度进程。当前单实例部署无影响。

## 12. 端到端数据流示例

### 12.1 AI 出题（最完整的一条链路）

```
前端 aiGenerate()
  → POST /api/question/ai-generate {knowledge_point_id, types, difficulty, count}
      → 路由查 KnowledgePoint 拿 subject / name
      → KnowledgeService.pull_chunks_for_matching(subject, name, top_k=10)
          → provider.retrieve_chunks → WS start_turn(capability=chat, tools=["rag"], knowledge_bases=[subject])
          → 引擎 RAG 检索 → 返回 JSON 数组 → 解析为 [Chunk]
      → QuestionService.ai_generate(chunks, ...)
          → provider.generate_questions → WS start_turn(tools=[])
              → LLM 生成 JSON 数组（或写文件 → _fetch_output_json 兜底）
          → 逐题 _is_duplicate 查重
          → create_question 写 t_question(source=AI)
      → 返回 {"saved": n, "questions": [...]}
  ← 前端提示「入库 N 道题」并刷新列表
```

### 12.2 练习答题与掌握度回流

```
GET /api/practice/tasks/{id}
  → build_paper：question_ids 已有 → 直接加载 / 否则题库配题 + AI 补题
  → paper：附已答状态，隐藏 answer
POST /api/practice/tasks/{id}/submit
  → 校验归属 → submit_and_judge（规则 or AI 判分）
  → 写 t_attempt_record + t_practice_record
  → progress.finished? → finish()
      → PlanService.apply_practice_result
          → compute_mastery(本次全部对错) → kp.mastery / mastery_count
          → _advance_schedule → interval_index ± → next_review_time
          → 任务 status=1 DONE
GET /api/plan/today → 该任务显示已完成；知识点页掌握度已变化
```

### 12.3 新建知识库并上传

```
前端 createKnowledgeBase()
  → POST /api/knowledge/deeptutor/kbs {name}      （REST 建空库）
  → (若有文件) apiForm POST .../{kb}/upload
      → provider.upload_documents（multipart，300s）
      → 检查 GET .../{kb}/config 的 index_versions
      → 为空则 POST .../{kb}/reindex 补建索引
  → 引擎后台解析、切块、向量化（状态由 pending → ready）
  → 前端 loadKbs 显示状态；随后可 search 或作为 AI 出题上下文
```

## 13. 运行时行为与降级

### 13.1 HTTP 错误映射

| 状态码 | 触发点 |
| --- | --- |
| 400 | 业务 `ValueError`（任务不存在、不属于当前用户、非练习任务、无答题记录、名称为空、查询为空等） |
| 401 | Token 缺失/过期/签名错误、用户不存在、登录密码错误 |
| 422 | Pydantic 参数校验失败（缺字段、类型错误） |
| 502 | 适配层调用引擎失败（建库、上传） |
| 500 | 未捕获异常（如 provider 中 `re` 未导入这类编程错误） |

### 13.2 降级矩阵

| 故障 | 系统表现 |
| --- | --- |
| DeepTutor 整体不可用 | `list_knowledge_bases` 回退本地目录或返回空；`retrieve_chunks` 返回空 → AI 出题入库 0 道；练习组卷降级为纯题库；判分降级为「子串匹配」规则 |
| LLM 返回非 JSON | 三层解析兜底；仍失败则判分走规则匹配、出题返回空 |
| 新库索引未初始化 | `upload_documents` 自动补 reindex |
| 题库无题且 AI 不可用 | 练习接口抛 400「暂无可用题目，请先录入或 AI 出题」 |
| 每日回流某次异常 | 记 `logger.exception`，协程继续，次日再试 |

## 14. 已知限制与改进点

按优先级排列，供后续迭代参考：

1. **多用户数据隔离不完整**：`/api/plan/tasks/{id}/complete`、`skip`、`/api/practice/*` 中的 task 校验已带 `user_id`（practice 有，plan 没有），`mapping` 审核接口也未校验归属。多租户上线前需统一收紧。
2. **知识点无唯一约束**：同一科目/章节/名称可重复创建，计划会重复排期。
3. **查重过于宽松**：`LIKE` 前 30 字，题面稍改即视为新题；建议改用 `semantic_similarity` 或 embedding。
4. **L3 匹配成本高**：`chunk × KP` 次 LLM 调用，50 条 chunk 可能跑几分钟；应改为批量打分或引入向量库预筛。
5. **`embed()` 已弃用但仍暴露在 Protocol**：调 `pipeline` 时若误用会拿到无意义向量（当前流水线已不走它），建议后续从 Protocol 移除。
6. **建表无迁移**：`create_all` 不处理字段变更，正式部署需引入 Alembic。
7. **定时任务单实例**：`_last_run` 为进程内状态，多 worker 会重复执行，需分布式锁。
8. **Token 存 localStorage**：存在 XSS 风险，可改 HttpOnly Cookie。
9. **`QuestionService.judge()` 死代码**：直接抛 `NotImplementedError`，应删除或实现。
10. **阈值口径**：代码默认 `auto=0.85 / review=0.60`，若概要设计文档写的是 0.7，需要统一（改 `config.py` 或改文档）。
11. **掌握度分档两套阈值**：前端 `masteryLevel`（[index.html](file:///D:/Smart/web/index.html#L486-L489)）用 40 / 70 / 90；后端 `mastery_summary`（[service.py](file:///D:/Smart/src/smart/knowledge/service.py#L107-L118)）用 25 / 55 / 85。同一批数据在两个页面可能显示不同档位，建议统一到一套。
